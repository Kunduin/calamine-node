# Tokio versus Rayon — 2026-09-19

Keep Tokio's `spawn_blocking` for the shipping implementation. Replacing only the
CPU executor with Rayon did not improve concurrent complete-read throughput in
this local comparison. This does not establish that Rayon is generally slower;
it gives no reason to add another executor to this binding now.

## Controlled change

Both builds use the same Calamine version, one-copy Buffer snapshot, automatic
waiting, cancellation, JS facade, batch sizes, and complete JS output. Both use an
explicit reader concurrency of twelve on an Intel Core i5-12400 with six physical
cores and twelve logical CPUs. The shared environment is:

```sh
TOKIO_WORKER_THREADS=12
RAYON_NUM_THREADS=12
UV_THREADPOOL_SIZE=12
```

The alternative changes `ActiveTask::run` to `rayon::spawn`, returning through a
Tokio oneshot channel. It retains Tokio for napi-rs futures and semaphore waits.
Panics are caught and mapped to the existing native error shape. The execution
permit remains held until the operation finishes. This tests a CPU-executor
replacement, not a redesign that removes Tokio or parallelizes Calamine internally.

See the [experimental patch](rayon-experiment.patch) and
[raw results](rayon-2026-09-19.json), including source notes, fixture hashes,
artifact hashes, all samples, CPU time, heartbeat gaps, and process peak RSS.
Rayon is not a shipping dependency.

## Complete-read results

Node 22.23.2, Linux x64. Times below are medians of five measured batches after
one full-batch warmup, in milliseconds. Each case runs in a fresh process, with
forced GC before each measured batch. Cases run sequentially, Tokio before Rayon;
this is a local comparison rather than a randomized benchmark study.

| Input per file               | Requests | Tokio elapsed | Rayon elapsed | Tokio main-thread CPU | Rayon main-thread CPU |
| ---------------------------- | -------: | ------------: | ------------: | --------------------: | --------------------: |
| 1M numeric cells, Buffer     |        1 |         330.0 |         326.6 |                  80.2 |                  82.6 |
| 1M numeric cells, Buffer     |       10 |        1090.8 |        1127.7 |                 819.2 |                 831.0 |
| 1M numeric cells, local file |       10 |        1087.3 |        1140.0 |                 787.1 |                 821.4 |
| 100K string cells, Buffer    |        1 |          81.5 |          80.9 |                  27.5 |                  28.0 |
| 100K string cells, Buffer    |       10 |         345.4 |         439.8 |                 253.9 |                 352.3 |
| Small XLS fixture, Buffer    |      100 |          22.0 |          35.5 |                  21.6 |                  34.7 |

Single-file times are close. Concurrent numeric cases show no clear Rayon gain;
the individual samples overlap. String and small-file cases were slower with the
Rayon bridge in this run. Their main-thread CPU also increased, so the elapsed
difference cannot be attributed solely to native queue overhead. Allocation,
completion timing and GC can change when an executor changes; these measurements
do not isolate a single cause.

Inputs are prepared before timing. The timed work includes Buffer snapshots,
parsing, JS value construction and native cleanup. `Promise.all` retains complete
results until the last request finishes. Ten requests use independent copies of
the same synthetic workbook; the XLS case uses 100 copies of the repository's
licensed `cells.xls` fixture. These are not production ingestion measurements.
Main-thread CPU includes synchronous Node-API work and GC, not just JS source.
Bun passed functional tests; these performance numbers are from Node only.

## Native artifact size

Both are release builds for `x86_64-unknown-linux-gnu` with the same Rust profile.
Compressed sizes use gzip level six and are not npm package sizes.

| Executor             | Native bytes | Gzip bytes |
| -------------------- | -----------: | ---------: |
| Tokio 1.53.1         |    2,405,528 |  1,036,435 |
| Tokio + Rayon 1.12.0 |    2,419,384 |  1,054,909 |
| Difference           |      +13,856 |    +18,474 |

Size is a small increment here. The decision to keep Tokio comes from the lack of
a measured throughput benefit and avoiding another execution/result bridge.

## Reproduction and validation

Apply the patch in an isolated checkout of the revision containing this report,
then run `pnpm build` and `pnpm test`. Prepare input copies named `0.xlsx` through
`9.xlsx` and run the helper against each independently built package:

```sh
TOKIO_WORKER_THREADS=12 RAYON_NUM_THREADS=12 UV_THREADPOOL_SIZE=12 \
  node --expose-gc scripts/benchmark-concurrency.mjs \
  /path/to/package /tmp/numeric-copies buffer 10 12 5
```

For the small XLS case, make 100 copies and use `buffer 100 12 5`. The helper's
`.xlsx` filenames are merely lookup names for this Buffer case: Calamine detects
XLS from the bytes. Do not use that renamed fixture to benchmark path-based format
selection.

The isolated Rayon build passed 7 Rust tests and the same 45 integration tests on
Node and Bun. The shipping Tokio build additionally passed `pnpm check` and
`pnpm pack:check`. No production servers or databases were used.

Tokio's [blocking-task guidance](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)
recommends limiting CPU-heavy work and identifies Rayon as an alternative.
Rayon's [spawn API](https://docs.rs/rayon/latest/rayon/fn.spawn.html) explains its
global-pool and panic behavior. Neither executor parallelizes a sequential
Calamine operation merely by running it on a different pool.
